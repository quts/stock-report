# AI Investment Research Agent — Codex Prompt 草稿 V0.1

> 狀態：討論草稿（尚未定稿）  
> 語言：繁體中文  
> 目的：作為 Codex 後續架構設計與 MVP 實作的共同規格。  
> 文件定位：通用投資研究報告規格，採用「事件 → 市場 → 機構觀點 → 產業／供應鏈 → 風險 → 結論」的研究結構，不引用或改寫特定第三方報告內容。

## 1. 角色與目標

你是一位資深 Python Software Architect、Financial Data Engineer 及 AI Agent Engineer。

設計並實作一套 **AI Investment Research Agent**，模仿專業投顧研究員的分析流程：從指定股票或事件出發，自動蒐集可信資訊、驗證、統計投顧評等、分析市場與產業影響，最終產出 **繁體中文 1–2 頁 A4 PDF 投資研究報告**，並保留可稽核 JSON 研究資料。

基本原則：

- 盡可能自動化資料蒐集、驗證、分析及報告生成。
- 所有數字、事件、評等及機構名稱必須可以追溯原始資料；不可捏造。
- 明確區分「已驗證事實」、「投顧觀點」、「AI 推論」和「未驗證傳聞」。
- 遇到來源衝突或缺少證據時標示不確定性，不得要求模型自行猜測。
- 系統統計外部投顧的 Buy / Hold / Sell 共識；**不得把評等直接改寫成『立刻買進／持續持有／立刻賣出』的即時交易指令**。
- 採務實、低成本、可測試及易維護的 MVP；避免過早採用多 Agent 或分散式架構。

## 2. 輸入與研究範圍

第一階段支援：

- 股票代碼：如 NVDA、AMD、2330.TW（需確認交易所與市場）。
- 研究截止時間（含時區）及資料擷取時間。
- 研究區間：例如最近 7／30／90 天。
- 可選的特定事件主題。
- 報告語言：繁體中文。
- 輸出：結構化 JSON、1–2 頁 PDF。

MVP 一次處理一家公司，但資料模型與 CLI 應保留批次執行能力。未來可擴充為「輸入事件 → 自動尋找相關上市公司及供應鏈」。

## 3. 報告的研究結構

模仿典型投顧研究報告，涵蓋以下六個分析模組：

1. **事件時間軸**：事件發生時間、媒體發布時間、官方公告，以及相關說法是否獲確認。
2. **市場反應**：標的股價、成交量、同業及主要指數的同期變化，清楚註記盤中、收盤或盤後。
3. **機構觀點**：各投顧最新有效評等、升降評、目標價及其修正。
4. **產業與供應鏈**：直接受益／受損者、上下游、競爭對手，說明因果機制與反證。
5. **風險與情境**：公司治理、技術路線圖、需求、估值、政策及資料不確定性。
6. **研究結論**：機構共識、主要分歧、後續追蹤指標、可能推翻結論的條件。

不得只憑同時發生的價格變動就宣稱事件與股價有因果關係。

## 4. Data Provider 與資料來源

設計可擴充的 Provider / Adapter 介面，涵蓋：

### A. 新聞、重大事件
- 公司官方 Investor Relations、監管機關公告與申報。
- 主流財經媒體、新聞 RSS／索引（可評估 GDELT）。
- 原始來源與二手轉載的辨識。

### B. 市場及財務資料
- 交易所行情、歷史價格與成交量。
- 市值、估值、季度／年度財報、財務指標。
- 同業、產業 ETF／指數及事件窗口的可比報酬。
- 美國申報資料可評估 SEC EDGAR / XBRL 官方 API。

### C. 機構評等
- 投顧機構／分析師識別碼。
- 原始評等文字、標準化分類、發布時間與適用期間。
- 升評／降評／維持／首次覆蓋，以及目標價修正。
- 來源網址與資料供應商識別碼。
- 可評估 Financial Modeling Prep 或其他合法授權的評等供應商，先確認付費層級、覆蓋市場及授權限制。

### D. 產業及供應鏈
- 公司申報的營收依賴程度、客戶、競爭者。
- 公開且有來源的供應鏈關係與產品路線圖。
- 區分已公開的商業關係與模型推測的潛在轉單。

**不得假設免費 API 可以完整取得逐機構評等**；若缺少資料應揭露覆蓋不足，不能以新聞提及數推估機構數。

## 5. Evidence / Validation Pipeline

必須保留以下欄位：

- `event_time`、`published_at`、`retrieved_at`、`research_as_of`，全程保留原始時區並標準化。
- `source_url`、`publisher`、`source_type`、`claim_id`、`verification_status`。
- 可重現的原始資料快照／摘要及供應商回傳紀錄（遵守授權）。
- 數字的貨幣、單位、價格基準及資料版本。

驗證規則：
1. 優先核對公司與監管機關的第一手資料。
2. 將跨媒體轉載的同一原始消息去重，不能誤算為獨立驗證。
3. 重大指控、管理層變動及監管事件需有充分證據；未查證者標記 `Unverified`。
4. 相互衝突的來源不得無聲合併，應保留衝突、來源及時間。
5. 報告中的關鍵陳述應關聯到來源 ID；數字與評等需可回溯原始紀錄。
6. 無法取得、過時、模糊或品質不足時使用 `Unknown`、`Unverified` 或 `Insufficient Data`，不得補值。
7. 相同輸入與資料快照應能重現相同的統計結果。

## 6. 投顧評等統計引擎

保留原始評等，另提供**可設定的標準化映射**：

| 五級標準化評等 | 三級彙總 |
| --- | --- |
| Strong Buy | Buy |
| Buy | Buy |
| Hold | Hold |
| Sell | Sell |
| Strong Sell | Sell |

對 `Outperform`、`Overweight`、`Equal Weight`、`Neutral`、`Underperform`、`Underweight` 等詞彙，依資料供應商與機構定義設定映射規則；存在歧義時列入人工查核或未分類，**不可由 LLM 自由解讀**。

統計規格：
- 同一機構對同一標的，截至報告時間只採計最新有效評等，避免重複計算。
- 分開顯示機構數（distinct firms）、分析師數與評等筆數，不能混為一談。
- 輸出 Buy / Hold / Sell 數量、比例、總有效機構數、未分類數與資料覆蓋範圍。
- 與上一研究窗口比較，顯示升評／降評／維持／首次覆蓋及共識變化。
- 列出主要機構的最新評等、日期、目標價、原始來源。
- 每筆評等記錄市場與股票代碼，避免 ADR、不同股類或交易所混淆。
- 當樣本不足、評等過期或資料缺失時明確標示，不產生誤導性百分比。
- 研究評等不是對使用者在當下交易的指令；不擅自加入「立刻」字眼。

未來可加入投顧歷史表現統計（評等發出後 30／90／180 天的基準調整報酬），須注意前瞻偏誤、存活者偏誤、目標價期限及價格調整。

## 7. AI 分析引擎

以**已驗證且具引用的資料**生成：
- 重大事件摘要及時間軸。
- 價格反應與同業比較。
- 公司營運及競爭地位的短／中／長期情境。
- 主要競爭對手、上游及下游供應鏈的潛在影響。
- 機構評等共識、分歧與近期變化。
- 關鍵風險、反面證據與待觀察指標。

LLM 輸出需透過 JSON Schema / Pydantic 驗證，且每一項關鍵結論關聯 `evidence_ids`；對沒有證據的推論應明確標註假設。採可替換 LLM Provider，不在模型中直接計算投顧統計或市場價格。

## 8. PDF 排版（最多兩頁）

**第 1 頁：事件及產業分析**
- 標題、股票代碼、報告日期、資料截至時間。
- 3–5 句重點摘要。
- 重大事件時間軸與查證狀態。
- 同期股價／同業比較小圖表。
- 受惠及承壓的公司／供應鏈。
- 主要風險及反證。

**第 2 頁：投顧共識及研究結論**
- Buy / Hold / Sell 機構數、比例與趨勢。
- 主要投顧機構最新評等、目標價及評等變化。
- 競爭者／供應鏈影響整理。
- 綜合研究結論與可能反轉的條件。
- 方法、資料覆蓋率、資料截至時間、引用來源（URL 或可追溯 ID）及免責說明。

要求：
- A4，繁體中文，中文字型需正確嵌入或使用可合法分發的字型設定。
- 版面要有專業投顧報告的表格、時間軸與簡潔圖表；不得靠縮到無法閱讀的字體塞入內容。
- 自動控制篇幅；超出上限時依重要性裁切摘要，但不能移除必要引用與資料限制。
- 內容具有來源歸屬，並避免重製或轉載受著作權保護的整份原始報告。

## 9. 技術與架構

- Python、模組化架構及 Adapter Pattern。
- Pydantic 資料模型與 JSON Schema。
- SQLite 保存研究記錄、資料快照、評等與引用；保留日後升級 PostgreSQL 的可能性。
- 可替換 LLM Provider。
- HTML + Jinja2 + PDF renderer（可評估 WeasyPrint）。
- CLI 操作；後續再增加定期排程與 Web UI。
- Retry、Rate Limit、Caching、Logging、錯誤處理及可觀測性。
- API Key 從環境變數或安全設定讀取，不得寫入程式碼。
- 程式碼、Script、註解、變數與函式名稱使用英文；文件與 PDF 內容使用繁體中文。

## 10. 測試與品質門檻

建立 Mock Provider 和固定資料集，以便不依賴付費 API 的 CI 測試。至少涵蓋：
- 相同新聞事件跨媒體重複轉載。
- 報導和官方公告時間不同或內容矛盾。
- 未證實的 CEO 更替及其他重大指控。
- 同機構不同分析師、同一機構多次評等與最新評等判定。
- 評等詞彙映射、未知分類、缺失資料、評等過期。
- 時區、盤前／盤後、價格與百分比計算。
- JSON Schema 檢查與證據引用完整性。
- PDF 頁數、中文字型、文字溢位及來源註記。
- 基於固定資料快照的完整 End-to-End Test。

## 11. MVP 交付

最短完整流程：

`Ticker + As-of Date → Providers → Evidence Validation → Analyst Consensus → AI Research → JSON → 1–2 page PDF`

優先完成單一股票研究；產出：
1. 簡明架構設計與資料流程。
2. 資料模型、API 選型與可得性／授權／成本評估。
3. 可執行的 CLI MVP。
4. 可重現的測試資料及測試。
5. 一份示範 PDF 與對應 JSON。

**執行方式：先提出技術架構、資料模型、API 成本與 MVP 範圍供審查，再開始實作。**

## 12. 自然語言操作介面與 Codex 整合（MVP 必要驗收）

**產品目標**：系統完成後，使用者在已配置此 Repository 與執行環境的 Codex 工作階段，僅需輸入一句繁體中文需求，Codex 即可操作研究系統，生成可取得的 PDF；不需要使用者手動執行 Python。

### A. 自然語言需求轉參數

- 支援範例：「研究 NVDA 最近 30 天的重大事件、股價反應、投顧買進／持有／賣出共識與台灣供應鏈影響，產出兩頁繁體中文 PDF。」
- 將自然語言解析成 **Pydantic 驗證的結構化 Request**，至少包括 `ticker`、`market`、`lookback_days` 或研究起訖時間、`research_as_of`、`topic`、`report_language`、`max_pdf_pages`。
- 支援中英文股票名稱、股票代碼與市場識別；有歧義或缺少必要參數才提問，其他欄位使用**文件化的預設值**，並在結果回報實際採用的設定。
- 不允許 LLM 任意拼接 shell 指令；先以 Schema 驗證，再以安全參數方式呼叫固定 CLI 入口。

### B. 穩定的 CLI 執行契約

- 提供單一、可由 Codex 呼叫的入口，例如 `python -m stock_report generate --ticker NVDA --lookback-days 30 --max-pages 2 --output-dir reports`；實際命令應以專案實作為準並寫入 README。
- CLI 負責完成：資料擷取 → 查核 → 機構共識統計 → AI 分析 → JSON → PDF，不能依賴 Codex 在對話中逐步手工拼湊報告。
- 輸出機器可讀的執行結果（如 `manifest.json` 或標準輸出 JSON），至少包含 `run_id`、`status`、`report_path`、`json_path`、`research_as_of`、資料覆蓋與警告清單。
- `reports/` 下每次研究產生獨立輸出目錄，避免覆蓋；預設忽略 Git 追蹤，除非使用者明確要求提交報告。
- 路徑應可在目前執行環境中存取，並提供取得生成 PDF 的明確方式；**不能保證不同 Codex 宿主環境都會自動提供附件下載**。

### C. Codex 操作指引

- 在 Repository 增加適用的 `AGENTS.md` 或獨立操作說明，規範 Codex 如何辨識研究需求、選擇 CLI、驗證參數、處理失敗以及回覆成品位置。
- Codex 應先檢查必要的 API Key、網路存取、套件與中文字型；不可宣稱已完成不存在的報告。
- 使用者只需提出自然語言研究需求；Codex 在允許的執行環境內完成調用，最後回覆：研究標的、期間、資料截止時間、PDF／JSON 路徑、主要限制與警告。
- 研究系統與 Codex **解耦**：即使不使用 Codex，仍可以直接透過 CLI、排程或未來 Web UI 執行相同的研究工作。

### D. 失敗處理與品質閘門

- 當缺少 API Key、無法連線、資料來源權限不足、評等覆蓋不足或驗證失敗時，回傳明確的結構化錯誤與處理方式。
- 區分 `success`、`partial`、`failed`；部分成功時 PDF 必須標示資料限制，並由可配置的品質門檻決定是否允許生成。
- 不得以虛構資料補齊缺漏；除非使用者明確選擇 Demo 模式，否則不能將 Mock Data 當成真實報告。
- 需要 API 費用或外部帳號授權的步驟，事前明確說明依賴，不得偷偷切換為未驗證來源。

### E. End-to-End 驗收測試

- 使用固定 Mock Dataset，在不連外的測試環境從「自然語言需求 → 解析 → CLI → JSON → PDF」完成一次全流程驗收。
- 至少驗證：Ticker 與研究期間正確、輸出路徑存在、JSON Schema 合格、PDF 為 1–2 頁、繁體中文正常顯示、每筆機構評等可追溯、警告有回報。
- 在具備合法資料 API 與網路權限的環境，進行至少一次真實資料 Smoke Test；不得把此結果混同於 Mock Test。
- **MVP Done Definition**：使用者於 Codex 輸入一句自然語言，不需自己執行 Python，即能取得有效的 PDF 路徑或附件，且失敗時獲得明確原因；相同研究流程亦可脫離 Codex 獨立執行。

## 13. 後續討論事項（尚未定案）

1. 是否在 MVP 就納入「事件驅動」：從事件識別受影響股票，而非僅單一 Ticker。
2. 評等資料 API 的選擇、台美股涵蓋率與月費上限。
3. 是否增加機構歷史評等準確率／回測。
4. 報告產生方式：手動觸發、定時更新或重大事件觸發。
5. 對來源不足、資訊衝突及估值結論採用何種具體品質門檻。
